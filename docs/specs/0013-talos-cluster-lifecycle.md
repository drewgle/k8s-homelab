# 0013 — Talos Kubernetes cluster lifecycle

**Status:** Accepted
**Serves goals:** Learning (k8s, Talos); distro evaluation; repo organization
**Planned files:** `infrastructure/ansible/playbooks/talos/02-cluster-create.yml`,
`add-node.yml`, `upgrade.yml`, `health-check.yml`,
`infrastructure/linux/talos/` (templates, versions)
**Amended by:** [0019](0019-single-cluster-mixed-distro.md)
**Superseded requirements:** TALOS-01 → 0019 MIX-02, MIX-03, MIX-04, plus
TALOS-12 for what stays Talos-local

## Context

Spec [0006](0006-vm-platform.md) leaves Talos VMs sitting in maintenance
mode with an API on 50000/tcp and no cluster. This spec covers what turns
them into Kubernetes nodes and keeps them running: config generation,
bootstrap, node addition, and in-place upgrades. It ends where
spec [0007](0007-gitops-bootstrap.md) begins — at a kubeconfig on the control
machine.

Since spec [0019](0019-single-cluster-mixed-distro.md) this is no longer a spec
about *a Talos cluster*. It is the Talos implementation of 0019's join contract
(MIX-17), for a cluster whose other nodes may run something else. Two
consequences run through the requirements below: cluster identity is not Talos's
to own any more (TALOS-12), and the bootstrap half of this spec only executes when
`control_plane_distro` is `talos`, while the node half executes whenever any node
declares `node_distro: talos`.

Everything runs from `localhost` through
[`talosctl`](https://www.talos.dev/latest/introduction/getting-started/)
against the nodes' machine API. There is no SSH to a Talos node and no shell
on one; the inventory marks these hosts `ansible_connection: local` for
exactly that reason.

## Requirements

- **TALOS-01** **Superseded by
  [0019 MIX-02, MIX-03, MIX-04](0019-single-cluster-mixed-distro.md) and
  TALOS-12.** *Historical text: The cluster's identity is one secrets
  bundle at `infrastructure/linux/talos/secrets.yaml`, generated once (`creates:`
  guard) and mode `0600`. It MUST NOT be regenerated by a re-run: new secrets
  against an existing cluster orphan it permanently. It is gitignored, and it is
  the one file whose loss means rebuilding the cluster.*
- **TALOS-02** Machine configurations are rendered per node from
  `templates/{controlplane,worker}.yaml.j2` into gitignored `generated/`,
  mode `0600`, with the node's own hostname and IP, from the cluster PKI bundle
  (0019 MIX-02) rather than from Talos-local secrets. Rendering is the only
  place a node's shape is decided; nothing is edited on the node afterwards.
- **TALOS-03** Versions come from `versions.yaml` only — never a literal in a
  playbook or template. `talos.installer` is Talos's own, in
  `infrastructure/linux/talos/versions.yaml`; `kubernetes.version` is cluster-wide
  and comes from `infrastructure/linux/cluster/versions.yaml` (0019 MIX-22).
  Renovate owns both files.
- **TALOS-04** `talosctl` on the control machine MUST match the pinned
  installer version; it is downloaded from the release matching
  `talos.installer` rather than assumed present.
- **TALOS-05** Apply order: control planes first, then workers, then
  `talosctl bootstrap` against the *first* control plane only. Bootstrapping
  more than one node forms split-brain etcd. The control-plane and bootstrap
  steps MUST run only when `control_plane_distro == talos` (0019 MIX-14); with a
  kubeadm control plane this playbook applies worker configs and nothing else.
- **TALOS-06** Bootstrap MUST be idempotent: an `AlreadyExists` response is
  success, not failure, so a re-run over a healthy cluster is safe.
- **TALOS-07** The playbook is only complete when `kubeconfig` has been
  written to `generated/` and `kubectl get nodes` succeeds against it. That
  file is the contract with spec 0007.
- **TALOS-08** `add-node.yml` MUST require an explicit
  `-e new_nodes='["..."]'`, MUST refuse to run when the cluster PKI bundle is
  missing (pointing at `00-cluster-pki.yml`), and MUST derive control
  plane vs worker from inventory group membership — `kubernetes_controlplane` and
  `kubernetes_worker` since 0019 MIX-13 — rather than from the caller.
- **TALOS-09** `upgrade.yml` MUST run `health-check.yml` before touching
  anything, upgrade control planes one at a time (`throttle: 1`), verify no
  node reports `NotReady` before moving to the workers, and prompt for
  confirmation unless `-e auto_approve=true`. Upgrades default to
  `--preserve` (keep ephemeral data) and `--stage` (apply on next boot).
- **TALOS-10** `health-check.yml` MUST be runnable at any time without
  changing state.
- **TALOS-11** The machine config MUST set `cni.name: none` and
  `proxy.disabled: true` (spec [0016](0016-cluster-networking-cilium.md)).
  Nodes are `NotReady` until the Cilium agent lands on them — the health check
  therefore runs after that, not before. Installing Cilium is **not** this
  playbook's job: there is one release for the cluster (0016 CNI-10), installed by
  a distro-neutral play.
- **TALOS-12** Supersedes TALOS-01. `secrets.yaml` is a **rendered artifact** of
  the cluster PKI bundle (0019 MIX-02), not the cluster's identity. It stays
  gitignored and mode `0600`, and it MUST be reproducible byte-for-byte by
  deleting it and re-rendering. Losing it costs a re-render; the bundle is what
  cannot be lost. The never-regenerate rule that made TALOS-01 dangerous to re-run
  now lives at MIX-03, on the bundle.
- **TALOS-13** Worker machine configs MUST render and join correctly under any
  `control_plane_distro`, carrying only `cluster.ca.crt` and never a CA private
  key (0019 MIX-05, MIX-19). Whether Talos workers remain fully *manageable* with
  no Talos control plane — and therefore no trustd to issue their `apid`
  certificates — is 0019's open question 2 and is unresolved; until it is answered,
  `control_plane_distro: talos` is the supported configuration for Talos workers.

## Interfaces

Consumes: `cluster_name`, `cluster_endpoint`, `cluster_vip`, `cluster_pod_subnet`,
`cluster_service_subnet`, `cluster_dns`, `kubernetes_dns_domain`,
`kubernetes_cni`, `control_plane_distro`, `kubernetes_install_disk`, and Talos's
own `talos.installer`; inventory groups `kubernetes_controlplane` and
`kubernetes_worker` filtered to hosts with `node_distro: talos`. Produces:
`infrastructure/linux/talos/generated/talosconfig` and, when Talos holds the
control plane, `infrastructure/linux/cluster/generated/kubeconfig` (0019 MIX-01,
0014 FLAT-10).

## Acceptance criteria

- [ ] From provisioned VMs, `02-cluster-create.yml` completes and
      `kubectl --kubeconfig=generated/kubeconfig get nodes` lists every node
      `Ready`.
- [ ] Re-running `02-cluster-create.yml` against the healthy cluster changes
      nothing and does not regenerate the cluster PKI bundle.
- [ ] Deleting `secrets.yaml` and re-running reproduces a byte-identical file
      (TALOS-12).
- [ ] No rendered worker config contains a CA private key (TALOS-13).
- [ ] `add-node.yml -e new_nodes='["k8s-worker-04"]'` joins one node and
      leaves the rest untouched.
- [ ] `upgrade.yml` moves every Talos node to the `versions.yaml` Talos version
      with no workload outage on a 3-control-plane cluster.
- [ ] `health-check.yml` reports the cluster healthy and changes nothing.
- [ ] With `control_plane_distro: flatcar`, this playbook applies worker configs
      only and runs no bootstrap (TALOS-05).

## Known limitations

- `helm` must be present on the control machine; the playbook checks for it
  and fails with a clear message rather than installing it.
- The 60-second `pause` after applying control plane configs is a fixed wait,
  not a readiness condition; on slow hardware the bootstrap retry loop is
  what actually saves the run.
- Kubernetes version skew is not validated against the Talos version at run
  time — `versions.yaml` carries a comment about the supported pairing, and
  nothing enforces it. Since 0019 MIX-22 this constrains the whole cluster, not
  just the Talos nodes, so the consequences of the gap are larger than they were.
- Talos workers under a non-Talos control plane may be unmanageable by `talosctl`
  even while working correctly as Kubernetes nodes (TALOS-13, 0019 open question
  2). This is the sharpest known limitation of the mixed-distro model.
