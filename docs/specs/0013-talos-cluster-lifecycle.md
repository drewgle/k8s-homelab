# 0013 — Talos Kubernetes cluster lifecycle

**Serves goals:** Learning (k8s, Talos); repo organization
**Planned files:** `infrastructure/ansible/playbooks/talos/02-cluster-create.yml`,
`add-node.yml`, `upgrade.yml`, `health-check.yml`,
`infrastructure/linux/talos/` (templates, versions)

## Context

Spec [0006](0006-vm-platform.md) leaves Talos VMs sitting in maintenance
mode with an API on 50000/tcp and no cluster. This spec covers what turns
them into Kubernetes nodes and keeps them running: config generation,
bootstrap, node addition, and in-place upgrades. It ends where
spec [0007](0007-gitops-bootstrap.md) begins — at a kubeconfig on the control
machine.

Talos is the repo's only node OS, so this spec describes *the* cluster:
Talos owns cluster identity, holds the control plane, and runs every worker.

Everything runs from `localhost` through
[`talosctl`](https://www.talos.dev/latest/introduction/getting-started/)
against the nodes' machine API. There is no SSH to a Talos node and no shell
on one; the inventory marks these hosts `ansible_connection: local` for
exactly that reason.

## Requirements

- **TALOS-01** The cluster's identity is one secrets
  bundle at `infrastructure/linux/talos/secrets.yaml`, generated once (`creates:`
  guard) and mode `0600`. It MUST NOT be regenerated by a re-run: new secrets
  against an existing cluster orphan it permanently. It is gitignored, and it is
  the one file whose loss means rebuilding the cluster.
- **TALOS-02** Machine configurations are rendered per node from
  `templates/{controlplane,worker}.yaml.j2` into gitignored `generated/`,
  mode `0600`, with the node's own hostname and IP, from the secrets bundle
  (TALOS-01). Rendering is the only place a node's shape is decided; nothing
  is edited on the node afterwards.
- **TALOS-03** Versions come from
  `infrastructure/linux/talos/versions.yaml` only — never a literal in a
  playbook or template. Renovate owns the file.
- **TALOS-04** `talosctl` on the control machine MUST match the pinned
  installer version; it is downloaded from the release matching
  `talos.installer` rather than assumed present.
- **TALOS-05** Apply order: control planes first, then workers, then
  `talosctl bootstrap` against the *first* control plane only. Bootstrapping
  more than one node forms split-brain etcd.
- **TALOS-06** Bootstrap MUST be idempotent: an `AlreadyExists` response is
  success, not failure, so a re-run over a healthy cluster is safe.
- **TALOS-07** The playbook is only complete when `kubeconfig` has been
  written to `generated/` and `kubectl get nodes` succeeds against it. That
  file is the contract with spec 0007.
- **TALOS-08** `add-node.yml` MUST require an explicit
  `-e new_nodes='["..."]'`, MUST refuse to run when `secrets.yaml` is
  missing (pointing at the cluster-create playbook), and MUST derive control
  plane vs worker from inventory group membership — `talos_controlplane` and
  `talos_worker` — rather than from the caller.
- **TALOS-09** `upgrade.yml` MUST run `health-check.yml` before touching
  anything, upgrade control planes one at a time (`throttle: 1`), verify no
  node reports `NotReady` before moving to the workers, and prompt for
  confirmation unless `-e auto_approve=true`. Upgrades default to
  `--preserve` (keep ephemeral data) and `--stage` (apply on next boot).
- **TALOS-10** `health-check.yml` MUST be runnable at any time without
  changing state.
- **TALOS-11** The machine config MUST set `cni.name: none` and
  `proxy.disabled: true` (spec [0016](0016-cluster-networking-cilium.md)).
  Nodes are `NotReady` until the Cilium agent lands on them — the health check
  therefore runs after that, not before. There is one Cilium release for the
  cluster, installed by `02-cluster-create.yml` after bootstrap
  (spec [0016](0016-cluster-networking-cilium.md)).
- **TALOS-13** Worker machine configs MUST carry only `cluster.ca.crt` and
  never a CA private key. Workers have no business holding the material that
  signs the cluster; a provisioning path that would place a CA key on a worker
  is a defect, not a shortcut.

## Interfaces

Consumes: `talos_cluster_name`, `talos_cluster_endpoint`, `talos_vip`,
`talos_pod_subnet`, `talos_service_subnet`, `talos_cluster_dns`,
`kubernetes_dns_domain`, `kubernetes_cni`, `kubernetes_install_disk`, and the
versions in `versions.yaml`; inventory groups `talos_controlplane` and
`talos_worker`. Produces: `infrastructure/linux/talos/generated/talosconfig`
and `infrastructure/linux/talos/generated/kubeconfig`.

## Acceptance criteria

- [ ] From provisioned VMs, `02-cluster-create.yml` completes and
      `kubectl --kubeconfig=generated/kubeconfig get nodes` lists every node
      `Ready`.
- [ ] Re-running `02-cluster-create.yml` against the healthy cluster changes
      nothing and does not regenerate `secrets.yaml` (TALOS-01).
- [ ] No rendered worker config contains a CA private key (TALOS-13).
- [ ] `add-node.yml -e new_nodes='["talos-worker-04"]'` joins one node and
      leaves the rest untouched.
- [ ] `upgrade.yml` moves every Talos node to the `versions.yaml` Talos version
      with no workload outage on a 3-control-plane cluster.
- [ ] `health-check.yml` reports the cluster healthy and changes nothing.

## Known limitations

- `helm` must be present on the control machine; the playbook checks for it
  and fails with a clear message rather than installing it.
- The 60-second `pause` after applying control plane configs is a fixed wait,
  not a readiness condition; on slow hardware the bootstrap retry loop is
  what actually saves the run.
- Kubernetes version skew is not validated against the Talos version at run
  time — `versions.yaml` carries a comment about the supported pairing, and
  nothing enforces it.
